## 1. 节点身份

### 1.1 现状

| 事实 | 证据 |
|---|---|
| `INFO` 回复六段：`widscan58\|<target>\|<PROTO_VERSION>\|<idf ver>\|<commit date>\|<phy ver>`——**不含任何唯一标识** | `commands.c:421-428` **[已由源码确认]** |
| 后端节点唯一键 = `(gateway_id, transport_addr)`，显示名禁止全局去重 | `models.py:195-205` **[已由源码确认]** |
| 中继拨号自带名字：`ws://<桥>/node?id=<名>` | `relay_pipe.h` / `ws_bridge.py:38` **[已由源码确认]** |
| 后果：同一块板换接线（USB ↔ 中继）= 后端眼里两个节点 | **[根据源码推断]** |

### 1.2 提案：`DEVICE?`

```
--> DEVICE?\n
<-- DEVICE <mac12hex>|<chip>|<boot_id>\n
```

- `mac`：`esp_read_mac(ESP_MAC_BASE)`，基址 MAC，只读、无写寿命、无隐私外泄面（示例值一律写 `aabbccddeeff`，不落真机 MAC——见 §7 Q1）。
- `chip`：沿用 `radio_caps()->target`，与 `INFO` 第 2 段同源，便于交叉核对。
- `boot_id`：每次启动生成、**不进 NVS**。它同时解决两件事：**区分"重启后 seq 归零"与"链路丢帧"**，以及**给 `t_ms` 的 49.7 天回绕一个复位边界**（`multi-node-spectrum.md` §3.2）。
  - 取法推荐 **`esp_timer_get_time()` 在 boot 时的低 32 位**，而不是 `esp_random()`：后者在本目标上依赖 RF 噪声源，而这块板子的 PHY 是扫描器独占的资源（`WIFI_MODE_NULL` 起 PHY 的既有约束），为一个 id 引入新的 RF 依赖不值得 **[根据源码推断]**。启动时刻的亚毫秒抖动 + 晶振漂移足以区分"同一块板的两次开机"。
- 后端侧：`DEVICE?` 是**可选探测**——回答就记下持久身份，`ERR unknown` 就维持现状。因此它不改变任何接入时序 **[已由源码推断]**。

## 2. 时间语义

### 2.1 帧里的 `t_ms` 到底是什么

| 属性 | 事实 | 证据 |
|---|---|---|
| 来源 | `esp_timer_get_time()/1000`，**开机以来毫秒** | `scanner.c:332,468,489` **[已由源码确认]** |
| 跨节点可比性 | **不可比**（各板各的里程表） | **[根据源码推断]** |
| 回绕 | `uint32_t` 毫秒，约 **49.7 天** | **[根据源码推断]** |
| `seq_metrics` | METRICS 与 LEVELS **共用同一条** seq | `scanner.c:60,331,467` **[已由源码确认]** |
| `seq_spectrum` | 独立第二条计数 | `scanner.c:60,249` **[已由源码确认]** |
| 推论 | 序号**只能在同类帧内查缺**，不能跨帧类型对齐 | **[根据源码推断]** |

### 2.2 提案：`CLOCK?`

```
--> CLOCK?\n
<-- CLOCK <uptime_ms>|<boot_id>|<rotations>\n
```

用途是**给网关做一次配对采样**：网关在发命令与收到回复两端各记一个本地时刻，往返中点即为该 `uptime_ms` 的本地对应点（架构 §3.4 的 ±20 ms 量级来自 M1 的 `INFO` 往返 9/12/43 ms **[已由真机实测]**）。`rotations` 用来把"计数"与"时间"绑在一起，便于检测回绕。

**明确不做**：不加帧内绝对时间字段、不开 SNTP、不动 `t_ms` 的含义。

## 3. 频谱帧元数据（本期不动，仅登记）

`frame_spectrum_t` 尾部有 **1 字节 `reserved`**（`frames.h:75`）**[已由源码确认]**，是未来 flags 的天然落点（例如：GROUP 边缘通道标记、校准失效标记、spur 命中数）。

本期**不用**它，理由：一旦定义语义，三份镜像 + 对拍夹具 + Web/Android 显示层同批改；而中继是透传，帧里塞什么它都不感知——所以真正的成本全在解析端，收益却不属于多节点 MVP。**触发条件**：需要向后端表达"这一帧的可信度"时再启动。

## 4. 能力声明：`CAPS?`

```
--> CAPS?\n
<-- CAPS device clock ports band flags_ver\n
```

- 空格分隔的**能力名列表**，无版本号、无键值——新能力就是新增一个名字，老主机忽略不认识的词即可 **[根据源码推断]**。
- **老固件不认 `CAPS?`** → 回 `ERR unknown` → 后端记 `undeclared`。这正是**已有的口径**（能力位 `undeclared` 是上一轮真机接入里已申报的缺口 **[已由真机实测]**），不新造第三种状态。
- 与后端 `capabilities.py` 对齐：设备声明只是能力的**来源之一**，不替代后端的能力模型。

## 5. 资源与风险

| 项 | 评估 | 依据 / 风险 |
|---|---|---|
| 新增命令 | 3 条（`DEVICE?` / `CLOCK?` / `CAPS?`） | 命令分派是字符串比较，非热路径 |
| Flash | **< 1 KB** **[需要实机验证]** | 三个 handler + 回复格式化；不新增 IRAM 段 |
| 堆 | **0** | 复用 `reply` 缓冲（P5）；**禁止**任何新的 `malloc`/`calloc` |
| 静态 RAM | 数十字节（格式化临时量走栈） | C5 静态 RAM 只剩几百字节 **[已由真机实测]**，需要构建后核对 map |
| RH 模式白名单 | **默认不放行** | RH 白名单是 `exact[]`/`prefix[]` 两张硬表（`commands.c:308-318`）**[已由源码确认]**；RotorHazard 服务端不会问这些 |
| 中继路径 | **天然可用** | 中继是"无信封"字节管道，命令按 `HEAD <line>` 原样转发（`relay_pipe.h:8-16`）**[已由源码确认]** |
| 帧/CRC | **零影响** | 不改帧（P1） |

## 7. 待拍板

- **Q1 文档与仓库里的 MAC 写法**：推荐全部用占位 `aabbccdd0000`，真机 MAC 只进本地库不进 git（与既有"推送前对象级脱敏扫描"是同一条纪律）。
- **Q2 帧内 flags（§3）本期不做**，同意？
- **Q3 RH 模式要不要为 `DEVICE?` 开白名单**：开了计时节点也能被持久识别；代价是动了 RH 白名单——那是与 RotorHazard 兼容性直接相关的一张表，动它需要理由。推荐**本期不开**。
- **Q4 `boot_id` 的取法**：三选一——① boot 时刻 `esp_timer_get_time()` 低 32 位（推荐，零新增依赖、零写寿命）；② `esp_random()`（唯一性更好，但给独占 PHY 的板子引入 RF 依赖）；③ NVS 单调计数（能答"这是第几次开机"，代价是每次启动一次写）。推荐 **①**；要区分第几次开机，网关侧的连接事件已经给了。
