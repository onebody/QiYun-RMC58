## 三、ChatGPT 的回复（原文整理）

## widscan58 真机数据录制与回归基线方案

针对你目前的环境（macOS、ESP32-C5 已通过 USB 连接、串口为 `/dev/tty.usbmodem21401`），我建议先完成一份 **60 秒左右、包含多种协议状态的真机录制文件**，并把它作为 Web 数据层重构前的原始回归基线。

核心原则是：**保存未经解析的原始字节流，保留设备真实输出的二进制帧、文本行和状态切换顺序，不要只保存浏览器解析后的图表数据。**

### 一、推荐方案与录制策略

- **首选：浏览器 Web UI 直接录制**
  适合先建立基线、验证现有页面录制与回放功能。操作最少，但更依赖 Chrome 的 Web Serial 连接稳定性。

- **推荐用于后续反复回归：Python 串口桥接**
  先让 Python 打开串口，再由浏览器通过 WebSocket 连接，避免 Chrome 直接接管串口时触发已知的 macOS TTY 状态问题。但桥接也需要验证是否完整转发数据、是否存在缓存或丢帧。

建议第一份基线包含以下阶段：

| 阶段 | 建议时长 | 操作与目标 |
| --- | --- | --- |
| A. 稳态 | 15 秒 | 默认 METRICS FULL，观察常规数据帧 |
| B. 指标切换 | 10 秒 | 切换到 RSSI/SNR，观察 LEVELS 帧及恢复 |
| C. 掩码变化 | 10 秒 | 修改 ENABLE 掩码，检查配置切换与数据变化 |
| D. 恢复测试 | 10 秒 | 发送 REBOOT，观察重启、重新连接及恢复输出 |
| E. 结束稳态 | 15 秒 | 恢复默认配置，确认数据流重新稳定 |

总时长约 60 秒。**前提是当前固件确实支持这些命令及对应帧类型**；具体命令参数应以仓库当前版本为准，不要直接猜测 `ENABLE` 的掩码值。

### 二、开始前检查：串口占用与 macOS VMIN

#### 1. 确认设备存在

在 macOS 终端执行：

```Bash
PORT=/dev/tty.usbmodem21401

ls -l "$PORT"
ls -l /dev/cu.usbmodem21401
```

如果两个节点都存在，后续 Python 桥接优先尝试 `/dev/cu.usbmodem21401`；你当前遇到问题的 TTY 节点则按要求检查 `/dev/tty.usbmodem21401`。两者是同一 USB 串口设备的不同访问入口，不要同时打开。

#### 2. 检查是否有其他程序占用

```Bash
lsof "$PORT"
lsof /dev/cu.usbmodem21401
```

如果出现 `screen`、`python3`、`esptool`、串口监视器等进程，先确认它们是否正在使用设备。退出相应程序，再检查一次。

不要在不确认进程用途的情况下直接杀掉系统进程。

#### 3. 修复 VMIN=0

之前运行过 pyserial 或 esptool 的程序可能留下不合适的终端参数。按你已确认的故障处理方式，先执行：

```Bash
stty -f /dev/tty.usbmodem21401 min 1
stty -f /dev/tty.usbmodem21401 -a
```

检查输出中是否包含 `min = 1`（不同 macOS 版本的输出格式可能略有不同）。

如果仍然无法正常连接：

1. 关闭 Chrome 中已连接该设备的页面。

2. 退出其他串口程序。

3. 按一下开发板上的 `RESET`，等待设备重新枚举。

4. 重新检查设备节点：

```Bash
ls -l /dev/tty.usbmodem*
ls -l /dev/cu.usbmodem*
```

如果设备名称改变，更新后续命令中的串口路径。

**注意：** `stty` 调整的是终端属性，不会自动结束占用串口的程序。如果仍有程序持有设备，先处理占用，再尝试修复。

#### 4. 记录当前固件与代码版本

在项目根目录执行：

```Bash
git status --short
git rev-parse HEAD
git describe --tags --always --dirty
```

把输出保存到基线记录中。若工作区有未提交修改，也要记录，因为基线对应的是实际运行的固件和网页代码，而不一定是某个干净的 Git 提交。

这条路径更适合你当前的 macOS 环境。串口由 Python 持有，浏览器只处理 WebSocket 数据，能绕开 Chrome 直接打开串口时的一部分兼容性问题。

如果需要显式指定端口或波特率，使用脚本实际支持的参数。不要把示例参数强行传给不支持它们的版本。

### 四、60 秒内的具体操作序列

为了让回归测试覆盖数据解析、配置变化、设备重启和重新同步，建议使用统一时间表。准备阶段先确认命令格式、合法掩码以及页面按钮与固件命令的对应关系。

#### 录制操作清单

*0/5 完成*

00–15 秒
FULL 稳态
不修改设置，保持默认 METRICS FULL。观察二进制帧、文本行和页面刷新是否稳定。
验收：记录默认 PROFILE、STATUS 与帧类型。

15–25 秒
RSSI/SNR 指标切换
通过 UI 或固件实际支持的命令切换至 RSSI/SNR 模式，保持数秒，再恢复 FULL。
验收：确认配置响应与 LEVELS 帧是否出现。

25–35 秒
ENABLE 掩码变化
选择一个已知有效的 ENABLE 掩码，观察被启用和禁用的指标变化。
验收：记录发送的掩码及切换前后的帧类型。

35–45 秒
REBOOT 恢复
发送固件支持的 REBOOT 命令，等待设备重新启动。
验收：观察启动文本、重新同步、PROFILE/STATUS 快照和数据流恢复。

45–60 秒
恢复默认并稳态
重新连接或等待恢复后，恢复默认设置并持续采集。
验收：确认数据流稳定，记录最终配置。

#### 每个阶段需要注意的细节

**A. **`METRICS FULL`** 稳态**

- 录制开始后不要立刻切换配置，先留出一段完整的默认输出。

- 记录 `PROFILE` 和 `STATUS` 的初始快照。

- 尽可能让设备处于稳定、可重复的射频环境中。如果需要测试动态 RSSI，可以在后续单独制作一份动态信号基线，避免影响这份基础基线的可比性。

**B. **`METRICS RSSI/SNR`** 与 **`LEVELS`** 帧**

- 通过页面现有控制项切换；如果只能通过串口发命令，确认桥接模式的命令转发方向和换行符规则。

- 记录切换命令发出的时间，以及收到首个相关响应帧的时间。

- 不要仅凭图表发生变化就认定协议正确，要保留原始数据，供后续逐帧检查。

**C. **`ENABLE`** 掩码变化**

- 使用一个可明确解释的合法掩码，不要使用未经验证的随机值。

- 如果协议允许，最好选一个能明显改变输出字段或帧种类的掩码。

- 记录旧值、新值、确认响应以及数据流变化。

**D. **`REBOOT`

这是整段采集中风险最高的环节。重启可能导致 USB CDC 短暂断开、串口设备节点重建、桥接连接中断或录制逻辑停止。

因此，先在录制前单独验证一次重启恢复流程。如果该命令会造成 USB 设备重新枚举，且现有桥接程序无法自动重新打开设备，不要为了凑齐 60 秒而冒险让唯一的基线录制失败。

更稳妥的做法是先录制一份不包含重启的连续 60 秒基线，再单独录制一份重启恢复测试。如果你希望把重启包含在同一文件里，则必须先确认当前实现能够跨越重启继续录制。

**E. 结束稳态**

- 如果设备恢复默认配置需要重新连接，优先确保录制器没有因断开而提前结束。

- 如果页面只在断开时下载文件，应按其既有行为结束录制，不要在数据仍未写完时直接关闭标签页。

- 完成后立即记录文件名、实际时长和异常现象。

### 五、验证 .widscan58 文件是否有效

文件成功下载只是第一步。至少需要检查文件头、帧解析、回放和数据量四项。

#### 1. 确认文件已完整落盘

在终端中定位实际下载文件：

```Bash
find ~/Downloads -maxdepth 1 -type f -name '*.widscan58' -print
```

然后替换成真实文件名：

```Bash
FILE="$HOME/Downloads/你的实际文件名.widscan58"

ls -lh "$FILE"
file "$FILE"
shasum -a 256 "$FILE"
```

建议将 SHA-256 保存到基线清单中。之后原始基线不再覆盖；每次重录都生成新文件。

#### 2. 检查文件头与初始快照

先从仓库确认 `.widscan58` 的文件格式定义和读取器实现，尤其是：

- 文件头是否包含版本、魔数或格式标识。

- `PROFILE`、`STATUS` 是文件头快照，还是录制开始后的首批数据帧。

- 文件是否有时间戳、记录数、长度字段或校验和。

- 二进制数据与文本行是如何区分的。

- 文件结束是否需要特定的终止记录。

如果项目已经有专用解析器或回放页面，**优先使用项目自身的读取器验证**，不要自行假设文件头是 JSON、固定字节长度或某种通用容器格式。

如果需要快速检查文件原始字节，可使用：

```Bash
xxd -l 256 "$FILE"
```

这只是查看前 256 字节，并不意味着这些字节一定是可读文本。

#### 3. 使用浏览器回放

在 Web UI 中找到项目现有的回放入口，选择刚才下载的 `.widscan58` 文件。

重点检查：

- 文件是否被识别，是否报告格式或版本错误。

- `PROFILE` 和 `STATUS` 快照是否合理。

- 频谱图、RSSI/SNR、状态栏是否能够更新。

- 切换 `METRICS` 和 `ENABLE` 前后，回放是否出现对应的状态变化。

- 重启阶段是否能正确处理启动文本、短暂数据间隔和后续帧。

- 播放到末尾是否正常结束，而不是无限等待、卡住或崩溃。

如果回放页面能加载，但切换阶段没有呈现任何变化，也不能直接判定协议有问题：可能是所选回放视图没有显示该类帧，需要进一步检查原始记录。

#### 4. 帧计数和数据量的合理性检查

如果项目提供帧统计、调试日志或协议解析工具，使用它统计完整帧数、各类帧数量、解析失败数和时间跨度。

至少记录以下数据：

| 指标 | 验收要求 |
| --- | --- |
| 文件大小 | 大于零，且与采集时长和实际输出速率相符 |
| 时间跨度 | 约 60 秒，允许重启造成短暂间隔 |
| PROFILE / STATUS | 能找到预期的初始状态信息 |
| FULL / LEVELS | 在对应配置阶段能观察到相关帧 |
| ENABLE 变化 | 能找到配置切换前后的数据证据 |
| 重启恢复 | 如果录入同一文件，能看到重启及恢复后的数据 |
| 回放 | 能加载并播放到末尾 |
| 解析错误 | 没有无法解释的帧损坏或持续失步 |

不要把“每秒 1050 帧”直接当作串口协议帧数。你提到的固件 1050/s 节流，需要先确认它限制的是采样次数、内部数据处理次数、频谱更新次数，还是实际输出记录数。

举例来说，如果它确实意味着每秒输出 1050 条独立记录，那么 60 秒就是 63,000 条记录；但如果只是内部采样频率，就不能这样推算文件中的帧数。

### 六、常见失败模式与规避措施

```text
1. Chrome 中途提示设备丢失
常见原因包括 TTY 状态异常、设备重新枚举、USB 连接不稳或另一个程序打开了串口。
处理：结束本次录制并保留文件；记录发生时间；检查 lsof、执行 stty ... min 1，必要时按 RESET。不要把中断文件作为完整基线。
2. 1050/s 节流导致数据量过大
不要在录制期间打开大量调试输出或高开销的浏览器日志。连续记录原始字节流，避免逐条 console.log、实时格式化和重复复制缓冲区。
如果出现丢帧，区分是固件节流、串口传输瓶颈、WebSocket 转发瓶颈还是浏览器录制器问题。不要仅凭文件大小推断是否丢帧。
3. macOS 或 USB 设备省电
录制期间保持电脑接通电源，避免系统睡眠、合盖休眠和 USB 集线器断电。优先使用稳定的数据线和直连 USB 端口。
可在录制前临时执行：
Bash
caffeinate -dimsu
录制结束后按 Ctrl+C 退出。该命令用于防止部分系统空闲行为导致录制中断，不保证所有 USB 省电机制都被禁用。
4. WebSocket 已连接，但数据不完整
确认桥接程序没有对二进制数据执行 UTF-8 解码、换行切分或文本拼接。原始二进制帧可能包含零字节和非文本内容。
同时检查 WebSocket 发送是否完整保留每个字节块的顺序，以及接收端录制器是否将二进制消息原样追加。
5. 文件下载成功，但回放失败
可能是录制提前终止、文件头未写完、结束记录缺失或格式版本不匹配。
不要直接修改原文件。保留原件，复制一份用于调试，然后对照项目现有回放读取器定位错误。
```
